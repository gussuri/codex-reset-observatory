# 予測確率ロギングの運用・観測マニュアル

本プロジェクトでは、1時間ごとの予測確率をクラウド（Supabase）に常時保存するためのトリガーとして、GitHub Actions のスケジュール（Cron）機能を使用しています。

このドキュメントは、自動ロギングの実行状況を正しく観測・追跡するための手順と注意点をまとめた運用メモです。

---

## ⚠️ スケジュール実行に関する重要な前提（仕様）

* **GitHub Actions のスケジュール（Cron）は遅延またはスキップします。**
  * 無料プランのパブリックリポジトリでは、実行スケジュール管理の優先順位が低いため、指定された時間（毎時34分）から **数十分〜1時間程度遅れて実行される** ことが頻繁にあります。
  * また、GitHub側の処理キューの混雑状況によっては、特定の時間帯の実行が完全にスキップされる場合もあります。
  * これはGitHub側のインフラ仕様による制限であり、コードやAPI側の不具合ではありません。

---

## 🔍 24〜48時間観測時の追跡手順

自動実行が正しく行われているかを検証する際は、**GitHub Actionsのログ** と **Supabaseの `prediction_history` テーブル** のデータを突き合わせて確認します。

### 1. Supabase 側でのデータ確認 (`logged_hour` と `recorded_at`)

Supabaseのテーブルブラウザ等でデータを確認する際は、以下の2つの時間カラムに注目してください。

* **`logged_hour` (一意のデータキー)**:
  * 予測確率を計算した時間帯を表すカラムです。時・分・秒を `00:00:00` に丸めて保存しています（例：`18:16` に実行された場合は `18:00:00`）。
  * **同一時間帯（同じ時間枠）に複数回APIが実行された場合、このキー of ユニーク制約により upsert（既存レコードの最新情報上書き）が行われます。**
  * そのため、**テーブルの「行数」だけを見て実行回数を判断しないでください。**
* **`recorded_at` (実際のレコード保存日時)**:
  * データが実際にSupabaseのDBにインサートまたはアップデート（上書き）された正確な瞬間（UTCタイムスタンプ）が記録されます。
  * 実際に自動実行がいつDBに到達したかを追跡する際は、この `recorded_at` を参照します。

### 2. GitHub Actions ログとの照合

GitHub Actionsの「Actions」タブから各ワークフローの実行ログを開くと、今回の改善により以下の情報が詳細に出力されるようになっています。

* **`GitHub Actions executed at: <UTC時間>`**:
  * GitHub側で実際にコンテナが起動してAPIを呼び出した正確なUTC日時です。これをSupabase側の `recorded_at` と照合することで、実行からDB保存までの遅延がないかを確認できます。
* **`HTTP Status Code: <数値>`**:
  * Vercelの本番APIが返したHTTPステータスコードです。正常なら `200`、認証エラーなら `401`、その他データベース連携エラーなら `500` などが表示されます。
  * `200` 以外のステータスが返ってきた場合、GitHub Actionsは自動的に実行失敗（赤❌）となり、アラートを検知しやすくなっています。
* **`Response Body` (APIレスポンス本体)**:
  * APIから返却されたJSONデータがそのまま出力されます。成功時は以下のような構造になり、実際に保存されたパラメータを検証できます。
    ```json
    {
      "ok": true,
      "action": "upserted",
      "logged_hour": "2026-06-29T09:00:00.000Z",
      "recorded_at": "2026-06-29T09:16:41.122Z",
      "probability_24h": 0.179,
      "probability_48h": 0.217,
      "expectation": "medium"
    }
    ```

## 🛠️ トラブルシューティング

1. **Actionsログで「401 Unauthorized」が発生している場合**:
   * GitHub Secretsに登録されている `CRON_SECRET` の値が、Vercelの本番環境変数に登録した `CRON_SECRET` と一致しているか再確認してください。
2. **Actionsログで「Database save failed」または「500 Internal Server Error」が発生している場合**:
   * Vercel側の環境変数 `SUPABASE_URL` または `SUPABASE_SERVICE_ROLE_KEY` が正しいキーになっているか、またSupabase側で `prediction_history` テーブルが正しく構築されているかを確認してください。
